# 架构分解规则（详细版 V1.0）

## 1. 目的
本文档为首席架构师技能（`chief_architect`）提供一套系统化、可操作的分解规则，用于将产品需求文档（`PRD.md`）转化为高层架构设计，并确保分解结果符合技术栈规范（`tech_stack.md`）和工程最佳实践。遵循这些规则有助于产生可维护、可扩展、边界清晰且具备韧性的系统设计。

## 2. 核心原则
在进行任何分解之前，必须始终牢记以下原则：

- **高内聚低耦合**：模块内部应高度相关，模块间依赖应最小化。
- **单一职责**：每个模块应有且仅有一个改变的理由。
- **业务边界对齐**：模块划分应围绕业务能力或领域边界，而非技术分层。
- **技术栈一致性**：所有模块必须使用技术栈规范中定义的组件，禁止引入未经授权的技术。
- **演进式架构**：分解应支持增量演进，避免过度设计。
- **错误与韧性优先**：设计必须考虑失败模式，确保系统在异常情况下仍能保持可预测的行为。
- **数据驱动设计**：明确数据的来源、流向和一致性要求。

## 3. 分解步骤

### 3.1 识别业务领域（领域驱动拆分）
- 阅读 `PRD.md`，提取核心业务功能，并绘制简单的领域模型。
- 使用**事件风暴**或**名词动词分析**技术，识别关键实体、聚合根、领域事件。
- **输出**：候选领域列表（例如：用户管理、订单处理、支付、库存、通知）。

### 3.2 确定服务边界（微服务/模块）
基于业务领域，决定哪些功能应划归为独立服务或模块。使用以下规则判断：

1. **独立生命周期**：如果某个功能可以独立开发、部署、扩展，应划为独立服务。
2. **数据所有权**：每个服务应拥有自己的数据存储，避免多个服务直接共享数据库。
3. **团队结构**（若已知）：按照“康威定律”，服务边界应与团队组织边界对齐。
4. **业务变化频率**：经常一起变化的功能应放在同一服务；变化频率不同的功能应分开。
5. **事务边界**：需要强一致性事务的功能尽量放在同一服务；允许最终一致性的可以跨服务。
6. **技术异构性**：若某个功能需要特殊技术栈（如 AI/ML、实时处理），可单独拆分。

**输出**：服务列表，每个服务包含：名称、核心职责、关键数据实体、对外接口。

### 3.3 划分前后端模块
对于每个业务功能，决定其属于前端还是后端：

- **前端模块**：负责用户交互、界面渲染、客户端状态管理、调用后端API。
  - **按页面或功能域划分**（例如：用户中心模块、商品浏览模块、购物车模块）。
  - **业务逻辑与UI分离**：将业务逻辑（Hooks/Stores）与 UI 表现（Components）明确分离，便于复用和测试。
- **后端模块**：负责业务逻辑、数据持久化、服务间通信、与外部系统集成。
  - 按服务边界划分（与上一步的微服务一致）。

**注意**：有些功能可能同时涉及前后端（如实时消息推送），此时应明确前后端各自的职责和通信协议。

### 3.4 技术约束检查
- **对照 `tech_stack.md` 验证**：每个提议的模块必须检查其技术选型是否在许可范围内。
- **处理缺失技术**：如果 PRD 需求（如“实时聊天”）在现有技术栈中缺少对应技术，架构师必须先提出技术栈扩展建议，经批准后方可引入新组件，或在设计中使用已有技术替代。
- **禁止引入未经授权的库/框架**：若必须引入，应记录理由并触发技术评审流程。

### 3.5 定义数据流与API契约
在服务之间以及前后端之间定义清晰的接口：

- **通信协议**：
  - 默认采用 RESTful API 或 GraphQL（根据 `tech_stack.md` 规定）。
  - 内部服务间可考虑 gRPC 或消息队列（如 RabbitMQ、Kafka），依据性能和数据一致性要求决定。
- **API设计规范**：
  - 使用资源导向设计，URL 代表资源，HTTP 方法代表操作。
  - 请求/响应格式统一为 JSON。
  - 错误处理应返回标准错误码和错误信息（遵循 RFC 7807）。
  - 分页、过滤、排序应遵循统一风格（如使用 `page`, `limit`, `sort` 参数）。
- **数据流向完整性**：
  - 明确定义数据是“推”（WebSockets/Server-Sent Events/消息队列）还是“拉”（REST/轮询）。
  - 为每个数据对象明确定义“唯一事实来源”(Source of Truth)，避免数据冗余和不一致。
  - 在 `system_design.md` 中描述主要数据流，包括：
    - 用户请求如何从前端流向后端服务。
    - 服务间如何调用或异步通信。
    - 数据存储与查询路径。

### 3.6 错误处理与韧性设计
- **所有模块必须包含失败模式分析**：例如，“如果数据库宕机，该模块如何反应？”、“如果下游服务超时，如何降级？”。
- **设计应对策略**：
  - 使用断路器、重试、超时、降级、缓存等模式。
  - 对于关键路径，考虑异步处理或消息队列持久化，避免数据丢失。
- **在任务描述中明确韧性要求**：分配给 `technical_lead` 的任务必须包含具体的失败处理规范。

### 3.7 技术栈映射
对照 `tech_stack.md`，为每个模块分配具体技术实现：

- **后端服务**：编程语言、框架、数据库、消息队列、缓存、日志、监控等。
- **前端模块**：框架、状态管理库、UI组件库、构建工具、测试工具等。
- **确保**：所有选型均在 `tech_stack.md` 许可范围内。若需求超出技术栈支持，按3.4节处理。

### 3.8 任务粒度控制
- **分配给 `technical_lead` 的任何任务预计开发时间不得超过 4 小时**。如果超过，必须进一步拆分为子模块或子任务。
- 任务描述应清晰、可测试，包含验收标准。
- 此规则确保任务可快速迭代和验证，便于后续优化。

## 4. 质量属性规则
除了功能分解，还必须考虑以下非功能质量属性：

### 4.1 性能
- 识别关键路径和热点数据，设计缓存策略（如 Redis）。
- 评估数据库查询效率，考虑索引、读写分离或分库分表。
- 对于大文件上传/下载，设计分块传输和断点续传。

### 4.2 安全
- 所有 API 必须进行身份认证和授权（如 JWT、OAuth2）。
- 防范常见攻击：SQL注入、XSS、CSRF、敏感数据泄露。
- 数据传输必须使用 HTTPS。
- 敏感数据（如密码、支付信息）必须加密存储。

### 4.3 可观测性
- 每个模块必须输出结构化日志（如 JSON 格式），包含请求ID、时间戳、级别等信息。
- 集成健康检查端点（`/health`），便于监控系统检测。
- 定义关键业务指标（如订单量、响应时间）并暴露给监控系统（Prometheus、Grafana）。

### 4.4 可扩展性
- 服务设计应支持水平扩展（无状态设计）。
- 数据库应考虑读写分离或分片，避免单点瓶颈。
- 使用消息队列解耦生产者和消费者，支持流量削峰。

## 5. 分解检查清单
完成初步分解后，使用以下清单进行自我审查：

- [ ] 每个模块是否有明确的职责描述？
- [ ] 模块间依赖是否明确且最小化？
- [ ] 是否存在循环依赖？
- [ ] 数据是否被多个模块直接共享（应避免）？
- [ ] 每个服务是否有独立的数据存储？
- [ ] API 设计是否满足 RESTful/GraphQL 规范？
- [ ] 是否考虑了错误处理和异常场景（超时、重试、降级）？
- [ ] 是否遵循了技术栈规范？
- [ ] 是否有性能、安全、可扩展性方面的潜在风险？
- [ ] 每个任务是否控制在4小时工作量以内？
- [ ] 是否有明确的数据流向图和唯一事实来源定义？

## 6. 处理例外情况

### 6.1 当业务需求模糊时
- 优先采用**最小可行分解**，先划分出最清晰的部分，模糊部分暂做标记，待后续迭代细化。
- 在 `system_design.md` 中注明不确定区域，并提出需要澄清的问题。

### 6.2 当技术栈无法满足需求时
- 记录需求与技术栈的差距，提出技术栈扩展建议，并说明理由（如性能需求、特定算法）。
- 将建议提交至技术决策委员会（或通过 `chief_architect` 的上级），等待批准后方可使用新组件。

### 6.3 当存在历史系统集成时
- 识别历史系统提供的接口和数据模型。
- 设计防腐层（Anti-Corruption Layer）隔离新旧系统，避免历史系统的设计污染新系统。
- 明确集成方式（API 调用、消息、数据同步等）。

### 6.4 当任务超过4小时粒度
- 强制拆分为多个子任务，每个子任务必须有明确的输入输出和验收标准。
- 将子任务列表写入 `to_lead.md`，并标注依赖关系。

## 7. 示例：电商平台分解（仅供理解）

**PRD 摘要**：构建一个电商平台，支持用户注册登录、商品浏览、加入购物车、下单支付、订单查询、库存管理、后台管理等功能。

**分解结果**：

| 服务/模块         | 职责                                       | 技术栈                            |
|-------------------|--------------------------------------------|-----------------------------------|
| 用户服务          | 用户注册、登录、个人信息管理               | Python + Django + PostgreSQL      |
| 商品服务          | 商品信息管理、分类、搜索                   | Go + Gin + Elasticsearch          |
| 购物车服务        | 购物车增删改查、合并                       | Node.js + Express + Redis         |
| 订单服务          | 订单创建、状态流转、查询                   | Java + Spring Boot + MySQL        |
| 支付服务          | 支付接口集成、支付结果处理                 | Python + FastAPI + 第三方SDK      |
| 库存服务          | 库存扣减、补货通知                         | Go + gRPC + MySQL                 |
| 前端（用户端）    | 用户界面、调用上述API                       | React + Redux + Axios             |
| 前端（管理端）    | 后台管理界面                               | Vue + Vuex + Element UI           |

**数据流示例**：
1. 用户在前端点击“下单” → 前端调用订单服务创建订单。
2. 订单服务调用库存服务锁定库存（使用分布式事务或最终一致性）。
3. 订单服务创建订单记录，返回待支付状态。
4. 前端引导用户支付，调用支付服务。
5. 支付服务处理完成后，异步通知订单服务更新订单状态（通过消息队列）。

**错误处理与韧性**：
- 若库存服务不可用，订单服务应返回“库存服务暂时不可用，请稍后重试”，并记录错误，避免订单创建失败导致数据不一致。
- 支付服务超时时，订单状态保持“支付中”，并启动后台补偿查询。

**任务粒度**：
- 订单服务的“创建订单”功能拆分为：① 接收请求并校验参数（1h）、② 调用库存服务（1h）、③ 写入数据库（1h）、④ 返回响应（1h）。但实际可合并为单个任务，因为4小时限制是针对整体任务，如果拆分后每个子任务仍超过4小时，则继续拆分。
